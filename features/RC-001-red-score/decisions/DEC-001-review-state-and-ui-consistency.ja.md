## 理由と採用しない案

- activeだけでは入力途中と削除を区別できない。deleted_atならactive 0/1の契約を保ち削除日時も記録できる。多状態enumも可能だが今回は採用せず、状態管理画面や削除復元機能を増やさない。
- 閾値NULLから削除を推測せず、旧判定との関係を保つためruleを物理削除しない。削除前に開いた編集画面からの保存は拒否する。
- 集計条件ANDは50≤A<70の範囲を表現できる。ORへの変更や任意のAND/ORエディターは結果／範囲を変更し、未確定である。
- DB／ACの既存の丸め例に画面を揃える。矛盾を正当化するだけの別例は追加しない。

## 影響と置換する定義

DB／DDL v2のactive=0に削除を含む定義を置き換え、読取り・中間保存・削除・copy・旧編集画面からの復活防止を追加する。Task 1/2/3/4/6/8、AC-G04/G05/G16/G19/G32を補足し、番号は維持する。点数削除を再実行待ちとする注記、同じ例の式2丸め、単元側選択欄の重なりは[checklist](../docs/v2/figma-update-checklist.ja.md)に従って修正する。

v1と既存の確認事項を維持し、migrationやアプリ変更は実行しない。AC-G05の集計条件部分だけが確認待ちであり、Q3/Q32/Q33や他の既知要件を再び未確定にしない。

## Lessons

1. 次の操作が異なる画面状態は保存データでも区別する。中間保存→再表示→削除→旧URLまで確認する。
2. AND/ORの適用範囲を条件種類ごとに示し、50≤A<70に対するA=40の反例で誤読を検出する。
3. 削除対象とcommit時点を区別する。点数削除、rule削除、参照不足による判定不能は別である。
4. 一覧と編集は同じ保存内容を示す。段階丸めでは閾値だけでなく、二つの閾値の間の点数の判定まで比較する。
5. nodeの存在だけでは表示／操作を証明できない。修正後画像でlayer、clipping、通常／単元の両方を確認する。
6. 一組のfeedbackをレビューしたことを全ライフサイクル検証と混同せず、範囲と未確認canvasを明示する。
7. 提出文書は設計と動作を完結して説明し、chat履歴・Q番号・回答待ちを入れない。根拠と承認状態は内部contextに保持し、文書の完成を顧客承認と混同しない。

## 残る検証

文書／DDLと例の確認は静的確認であり、DB／アプリを実行していない。Figmaの修正後画像と関連操作確認は別途必要。chat内の回答案は送信済みやANDの承認を証明しない。
